1. WHAT THE PRODUCT IS
----------------------
RiskSense AI is a conversational risk-assessment platform. An employee ("requestor") describes an incident
to a chatbot. The system identifies the employee's persona (job role), picks a matching scenario, asks guided
questions (MCQ / yes-no / number / free text), turns answers into structured facts, then a deterministic
engine applies hard rules and a scoring matrix to produce a 0–100 score, a classification
(monitor_only | risk | elevated_risk | issue), a confidence %, a plain-language explanation and a
recommended action. A human must accept / override / escalate; the AI never decides or scores.

Two product tiers: FREE (self-signup, MFA, intake, minimal retention/audit) and PAID (SSO, review dashboard,
full audit, reports, department routing, own "Corp. Instance"). Tier is a tenant setting, not a code fork.

Roles (exactly one per user): requestor, administrator (TAC content team), system_administrator (Bayshore), audit (read-only).

4. WHAT HAS BEEN BUILT, IN ORDER (with the "how")
------------------------------------------------
Sprint 0 — foundation (done)
  * Translated both client documents to Bangla; wrote kickoff plan; created the docs/ knowledge base.
  * Scaffolded both apps. Backend: env validation, request ids, envelope {data|error, meta.requestId}, error codes.
  * Auth: Firebase token verification; unknown identities auto-provision as FREE requestors in the "public" tenant;
    pre-invited accounts (seeded with "dev:" uid) get linked on first login. Our own app sessions enforce the
    15-minute idle timeout and one session per account (Firebase does not do this). Admin roles require MFA.
  * MFA decision (Travis): strict two factors on the free tier = Firebase password/Google + our email OTP
    (POST /auth/otp/request, then POST /auth/session {otpCode}). Rate limits, lockout after 5 wrong codes.
  * Audit log: per-tenant sequence + SHA-256 hash chain (prevHash). Model refuses updates/deletes. Nightly/ad-hoc verify.
  * Content templates for TAC (xlsx with 4 sheets: personas, scenarios, questions, scoring), CI workflows, clarification agenda.
  * Git initialised, akib pushed, CI green. No AI-tool references are committed to the app repos (owner rule).

Phase 2 — administrator content (done except T-028 department mapping and richer editors)
  * lib/versioned.ts: draft (editable in place) -> active (never mutated; editing creates the next draft version)
    -> deactivated (kept forever because assessments pin versions). One "current" per version group.
  * Personas, scenarios, questions reference each other by stable string keys (not ObjectIds). Scenario activation
    validates: persona active, every flow question (and branch follow-ups) exists and is active, every required fact
    is produced by a reachable question; then pins a questionSetHash.
  * Datasets: upload xlsx/json -> parse (template columns, ";" lists, "Label=value" options, yes/no coercion)
    -> Zod + cross-reference validation (file OR existing content) -> stored as validated/rejected with row-level errors
    -> approval by a DIFFERENT administrator -> activation applies through the normal services (so versioning and
    audit apply) including the scoring sheet (matrix "default" + hard rules "sheet_*").
  * Starter content built from the BRD question sets because TAC has not delivered yet:
    3 personas (Finance Officer, IT Support/Cybersecurity, Healthcare Compliance), 13 scenarios, 64 questions,
    scoring sheet. Loaded into Atlas via npm run seed:content. A test guards that it always validates and activates.
  * Rules: shared condition language ({factKey, op, value} | {all|any}); engine picks the lowest priority, ties -> most
    severe; change control draft -> approved (other admin) -> active; edits go back to draft.
  * Scoring: six factors (controlEffectiveness, impact, severity, likelihood, duration, regulatorySensitivity), each
    weight + scale + mappings (first matching condition -> value, else scale min); score = sum(weight * normalized value);
    contiguous thresholds; confidence = 70% required-fact coverage + 30% mean extraction confidence; < 60 ->
    Professional Consult; score exactly 0 -> error review. POST /scoring/simulate runs the same functions; golden set
    (src/modules/scoring/golden/starter.json) runs in CI.
  * Admin screens for all of the above (generic ContentManager; nested fields edited as JSON for now) + live simulator.

Phase 3 — chat engine (done, verified in the browser with the real OpenAI model)
  * Start: persona given or inferred (confidence >= 0.6, else the user picks from candidates; can override).
    Scenario selected from the persona's library (>= 0.5, else the persona's default scenario). Versions pinned.
  * Turns: MCQ / yes-no / number answers are structured immediately (no model call). Free text goes to the extractor;
    the asked fact is "settled" only if extracted, type-coercible and confidence >= 0.5, otherwise one clarification
    is asked and then the value is kept but flagged. Branch follow-ups are inserted at the front of the queue when the
    trigger value matches. Missing required facts get one re-ask. Then status intake_complete.
  * Submit: rules -> scoring -> explanation (model writes prose from computed numbers; never re-derives the class)
    -> recommended action -> awaiting_decision (or error_review). Decision: accept/override(reason >= 25 chars + new
    class)/escalate; only this path can close; the Mongoose schema hook rejects closed-without-decision.
  * Content resolution: a tenant without its own personas uses the public library.
  * Incident fixed during real-model verification: the extractor returned "unknown" side facts for every key and
    overwrote clicked answers -> now side facts only fill gaps, need >= 0.7 confidence, no placeholders (regression test).
  * Frontend: /chat start, /chat/[id] conversation with typed widgets, result card with the three decisions, /review list.

Test count: backend 97 (vitest + supertest + in-memory mongod). Frontend: typecheck + lint (no unit tests yet).

6. CONVENTIONS EVERY CONTRIBUTOR MUST FOLLOW
--------------------------------------------
* Requirement ids (FR-xx, NFR-xx, SEC-xx, AI-xx, DASH-xx) in commits, tests and docs. Rules text: docs/ai/BusinessRules.md.
* Never put scoring/classification logic in the AI layer. The model extracts and explains only.
* Never add update/delete paths for auditLogs. Never set assessment status "closed" outside assessments.service.decide().
* Never edit an active persona/scenario/matrix in place — use the versioned helper.
* Every request-path query is tenant-scoped. PAID features are gated by tenant.features.*.
* Frontend talks to the API only through lib/api/client.ts with generated types (npm run gen:api after npm run openapi).
* All repo content in English. No secrets in git (.env.example only). Do not push unless the owner asks; branch akib.
* After every task: update docs/ai (API/Database/BusinessRules/project-map), DecisionLog if a choice was made,
  and write docs/dev-notes/YYYY-MM-DD-<task>.md explaining file by file what/where/why.
